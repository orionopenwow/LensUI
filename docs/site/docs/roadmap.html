Lens UI — Where It Stands and Where It Can Go

Last updated: 2026-11-21

What Lens UI is today

Lens UI is a shell overlay, not yet a shell replacement. Windows Explorer (explorer.exe) is still running underneath: Lens hides the native taskbar and desktop icons, then draws its own Dock, Top Bar, Quick Settings, Command Palette, Widgets and notifications as eight transparent Tauri (WebView2) windows. A Rust/Win32 backend handles the parts a web view cannot: DWM titlebar colors, traffic-light caption buttons, tiling, audio sessions, media, folder icons and taskbar restore.

That is a sound base. The overlay approach is why quitting Lens returns you to stock Windows instantly.

First build checklist

  1. Build-Lens-UI.bat (or bun run tauri dev). Expect compiler errors; the most likely spots are listed per module in the agents' notes: tauri::window::Monitor path in lens_monitor (try tauri::Monitor), WinRT method names in win_notifications.rs mod toasts, Code:: / Modifiers:: names in the hotkey block, the for attr in [DWMWA_…] loop in win_dwm_engine.rs, REG_OPTION_VOLATILE in win_shell.rs.
  2. With everything at defaults, confirm the shell behaves as before (dark-theme shadows included).
  3. Then switch on one opt-in feature at a time.

Known gaps

  1. Light packs still need a human look, as do the Launcher, Overview, gallery and every new card.
  2. Blur is not real, and all windows are still created at startup (patches exist, not applied).
  3. No tests in the repo, no CI, csp: null, and an 11 MB windhawk_setup.exe in the folder.
  4. Global shortcuts Alt+A and Alt+` are taken away from other apps while Lens runs.

Directions

A. Make the overlay excellent (recommended next)

Lowest risk, biggest daily-use gain.

  • System tray host and a real notification center (UserNotificationListener).
  • Done: event-driven window list; injected hook off by default.
  • Create rarely used windows (Control Center, Widgets, Palette) on demand rather than at startup; every idle WebView costs memory.
  • Multi-monitor bars, and real acrylic/mica behind surfaces.
  • Done: color tokens, .lenstheme. Light packs need a visual pass.

B. True shell replacement

Lens becomes the shell: HKCU\Software\Microsoft\Windows NT\CurrentVersion\Winlogon\Shell points at lens-ui.exe and Explorer never starts as the desktop. Lens then owns everything Explorer did:

  • wallpaper and desktop icons, tray host, Start/launcher, startup apps (Run keys and the Startup folder);
  • Win-key shortcuts and the task switcher that Explorer normally provides;
  • UWP/Store app activation, which leans on Explorer more than classic apps do.

It needs a recovery path before anything else: a watchdog that relaunches Explorer if Lens crashes, a hotkey that restores the stock shell, and a per-user (never machine-wide) registry change. Do this only after direction A, because A builds most of the pieces B requires. Prior art worth reading: Seelen UI (Tauri, overlay model) and Cairo Shell with its ManagedShell library (tray hosting and shell replacement).

C. Theme platform

Treat packs as data: .lenstheme files (JSON plus optional CSS and wallpaper), a gallery in Control Center, per-app window rules ("terminal is always 85% opaque, borderless"), wallpaper-derived accent, time-of-day pack switching, and icon packs.

D. Workflow and local AI

Already the most distinctive part (action router, workflow recorder, tiling). Keyboard-driven tiling with layouts saved per virtual desktop, session restore ("Coding" reopens and re-tiles its apps), window rules, clipboard history, and an action router that can explain and undo what it did.

  1. Build and run both passes on Windows; fix anything the compiler finds. (next)
  2. ~~WinEvent-driven window tracking; injected hook off by default.~~ Done, unverified.
